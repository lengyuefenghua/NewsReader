# Timeline 刷新优化设计（先快后全）

- 日期：2026-03-01
- 项目：NewsReader
- 范围：仅设计讨论，不实施代码变更
- 目标：优化“时间线刷新”体验，优先提升首批结果可见速度

## 1. 背景与目标

用户当前反馈的主要问题是“时间线刷新体感慢”，并明确优先级为：

1. 首批结果更快出现（最高优先级）
2. 不是单纯追求总耗时最短

因此本设计核心是：在不大规模重构的前提下，将刷新体验从“整批等待”升级为“先快后全”。

## 2. 现状诊断（基于当前实现）

### 2.1 调度层面
`NewsRepository.syncAll` 采用全量源并发 + `Semaphore` 限流。该模式能提升吞吐，但缺少“首批优先”策略，导致首批完成的源不一定是高价值源。

### 2.2 状态与事件层面
`TimelineViewModel` 目前主要以“全量完成”语义收口（`UiEvent.RefreshCompleted`）。虽然列表数据流可增量更新，但用户缺少明确的“首批已就绪”反馈。

### 2.3 网络策略层面
连接参数为统一超时策略（通用配置），对“首批可见”目标不够友好：慢源可能长时间占用并发槽位，影响快源尽早产出。

## 3. 设计原则

1. **先快后全**：优先让用户尽快看到可读新增内容。
2. **最小改动**：避免修改数据库 schema，避免大规模架构重写。
3. **兼容现有链路**：保留现有全量刷新能力，新增分阶段路径供时间线使用。
4. **可度量**：以 TTFF（首批可见时间）为主指标评估效果。

## 4. 方案对比

### 方案 A：分层刷新 + 渐进展示（推荐）
- 阶段 1：首批快刷（Fast Lane）
- 阶段 2：后台补全（Full Lane）
- 优点：最契合“首批更快出现”的目标，体感收益直接
- 缺点：需要新增阶段状态和事件语义

### 方案 B：智能并发调度（动态调度）
- 基于历史耗时/失败率进行优先级调度
- 优点：兼顾首批和整体吞吐
- 缺点：需要维护统计信息与调参

### 方案 C：分片提交 + 反馈优化（轻量）
- 主要优化 UI 反馈节奏
- 优点：改动小
- 缺点：对“首批真实速度”提升有限，偏感知优化

### 推荐结论
采用 **A 为主，后续按需叠加 B 的轻量能力**。

## 5. 目标状态设计（两阶段刷新）

### 5.1 阶段定义
1. **Fast Lane（首批快刷）**
   - 仅刷新优先源（建议 3~5 个）
   - 目标：尽快产出第一批新增并可见
2. **Full Lane（后台补全）**
   - 继续刷新剩余源
   - 目标：最终完整同步并汇总

### 5.2 状态机建议（概念）
- `Idle`
- `FastSyncing(current, total, sourceName)`
- `FastReady(newCount, sourceCount)`
- `FullSyncing(current, total, sourceName)`
- `Completed(totalNew, failed)`
- `Error(...)`

### 5.3 事件语义建议
保留现有全量完成事件，并新增“首批就绪”事件用于提示：
- 首批已更新 X 篇，正在继续补全...
- 当首批新增 > 0 时可触发一次滚动到顶部（按策略控制）

## 6. 最小改动落点（实施时参考）

> 本节仅定义未来实施范围，不代表当前已实施。

### 6.1 `data/NewsRepository.kt`
新增两阶段刷新入口（不破坏原 `syncAll`）：
- 参数：`fastBatchSize`、`concurrentLimit`、阶段进度回调
- 流程：
  1. 源集合优先级排序
  2. 先刷 fast batch，返回首批统计
  3. 再刷剩余 batch，返回全量统计

### 6.2 `viewmodel/TimelineViewModel.kt`
`refresh()` 升级为两阶段驱动：
- 首批完成：发“首批就绪”事件
- 全量完成：沿用 `RefreshCompleted`
- `syncState` 文案区分“首批刷新中/后台补全中”

### 6.3 `ui/common/UiEvent.kt`
新增首批事件类型（示例字段）：
- `newArticles`
- `completedSources`
- `totalFastSources`

### 6.4 `ui/screens/TimelineScreen.kt`
最小 UI 变更：
- 监听首批事件并提示
- 进度文案按阶段切换
- 保持现有进度条组件复用

### 6.5 明确不做
- 不改 Room schema
- 不改 DAO 表结构
- 不引入复杂打分模型（首版仅轻量优先级）

## 7. 验收指标

### 7.1 核心指标（必须）
1. **TTFF（首批可见时间）**
   - 定义：点击刷新到第一批新增文章可见
   - 目标：相对基线降低 ≥ 30%

2. **首批命中率**
   - 定义：首批阶段是否出现新增文章
   - 目标：> 70%

3. **全量完成时间约束**
   - 目标：不明显劣化（建议不超过 +10%）

### 7.2 观测建议
- 记录：刷新开始时间、首批完成时间、全量完成时间
- 输出：每次刷新的阶段统计，用于后续调优

## 8. 风险与缓解

1. **首批快了但总耗时变差**
   - 缓解：保持补全阶段并发不降级；持续观测总耗时

2. **事件频繁导致 UI 抖动**
   - 缓解：首批事件只发一次；补全阶段做节流

3. **失败源影响首批体验**
   - 缓解：首批阶段单源失败快速跳过，不阻塞阶段完成

4. **自动滚动打断阅读**
   - 缓解：仅在新增且满足条件时触发（如顶部附近/会话仅一次）

## 9. 测试与验证建议（实施后）

1. 功能回归：
   - 单源刷新
   - 全源刷新
   - 无新增
   - 部分失败/全部失败

2. 性能对比：
   - 同一源集合对比优化前后 TTFF 与总耗时

3. 稳定性：
   - 弱网、高延迟、超时、4xx/5xx 场景

---

## 结论

在当前目标“首批结果更快出现”下，推荐先落地 **两阶段刷新（先快后全）**，并以最小改动方式接入现有架构。该方案能在可控风险下显著提升刷新体感，同时保留后续演进到智能调度的空间。
